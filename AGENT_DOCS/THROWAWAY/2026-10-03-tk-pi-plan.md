# The plan, in the order it should be built

Companion to `2026-10-03-pi-extension-recall-in-the-harness.md`, which holds
the findings. This note holds the order, the wiring points, and the gates. The
premise, restated because everything below depends on it: **the model owns the
graph calls; the extension owns memory recall and the session lifecycle.** No
per-turn context load.

## Decisions needed before Phase 1

| # | Decision | Recommendation |
|---|---|---|
| D1 | Extension in this repo (`extensions/pi-tk/`) or its own repo? | In repo. The Phase 1 and 2 changes move with it, and `AGENT_DOCS/` is where the reasoning lives. |
| D2 | May the extension start the resident? `03-COMMANDS.md` says opt-in, never automatic. | Yes, default on, behind a config key, with an ADR. Without it every model-initiated kg call pays ~4.9s. |
| D3 | `deferred` or `direct` exposure for the 30B? | `deferred` default; `direct` as a config switch. A/B it against the real model — this is a measurement, not a preference. |
| D4 | Which profile does the pi extension register? | A new `compact`, not `memory` (22). Compounds plus reads; writes stay unreachable by the model. |

## Phase 0 — Measure. Blocking, and cheap.

Nothing below should be built on an unverified number.

```bash
mise run bench-real REPO=/path/to/repo      # one-shot vs resident, per tool
```

Record, in a throwaway note, with the commands that produced them: `tk mcp`
`tools/call` wall time for `search_graph`; the same for an **empty**
`search_graph` (expect two spawns — `callStructured` runs a coverage probe);
`tk explain --json` against three raw calls. Then confirm the resident flips the
first two.

**Gate:** if `tk mcp` is *not* ~4.9s per call, the code read in F1 is wrong and
Phase 1 is a different change. Re-plan rather than proceed.

## Phase 1 — Resident dial in `internal/mcp`. The load-bearing change. **SHIPPED 2026-10-03.**

ADR `history/DECISIONS/2026-10-03-mcp-dials-a-running-resident-before-it-spawns.md`.
Dial in `Server.runJSON`/`runStructured`, three outcomes kept distinct, `backend`
in `tk.log`, 9 new tests including a real unix socket. Gate: `search_graph` over
stdio, resident up **16.6ms** / resident down **4411ms**, byte-identical
payloads. `mise run e2e` 135+146 pass; `e2e-real` 9 subtests pass against CBM
0.11.0.

**Target it serves.** Every call inside an agent loop under 500ms, ideally
100ms. Measured over the socket, 10 of 12 tools already sit at 14–30ms; without
the dial every one of them is 2008ms. The dial is what makes the target
reachable, not an optimization. Full table and the two tools that break it:
`2026-10-03-latency-budget-and-operator-surface.md`.

Wiring point: `internal/cli/mcp.go:43-46`, where the `mcp.Server` is built from
`ctx`. Every other capability there is already a nil-safe hook
(`ShardsFor`, `EnsureIndex`, `Staleness`, `ProjectRoot`, `Projects`), so this is
one more hook of the same shape:

```go
s.Resident = func(rctx context.Context, tool string, args map[string]any, structured bool) (cbmexec.Result, bool, error)
```

backed by `resident.Client{Addr: ctx.Paths.ResidentSocket()}`, and consulted in
`callTool` before `s.Run.RunJSON` / `RunStructured`.

Non-negotiables carried over from `Ctx.residentTry`
(`internal/cli/root.go:236-268`) — the three outcomes stay distinct:

* **absent** (no socket) falls back to the spawn. Normal, not an error.
* **refused** (the engine said no) is an error, never a fallback and never an
  empty result. Folding it into "absent" reports a failed call as a clean miss.
* **answered** returns the result the same `ParseResult` path a spawn uses, so
  render parity stays structural.

Reads only. `source_search` already has its own refresh; writes never share the
child.

Tests: dial-first ordering; fallback when the socket is gone; refusal is not
absence; `Structured` flag passes through; **zero** engine spawns when the
resident answers (the resident test already has a fake that can count —
`fe357a9`), and one when it does not. Plus one assertion in `tests/e2e_mvp1.sh`.

Docs: new ADR, then `04-MCP.md` gains the dial-first order and the fallback.

## Phase 2 — Compounds, profiles, and the portable channels

All four are additive except the first, which is a contract change.

1. **`find` and `explain` over MCP.** `04-MCP.md` already mandates the compound
   form and the surface does not provide it. Their payloads are tk's, not the
   engine's, so "CBM's payload passes through verbatim" stops being true for
   those two tools — ADR, and `04-MCP.md` states which tools are pass-through and
   which are composed. **Justification corrected by measurement:** after P1,
   three separate calls cost ~45ms of engine time, so the compound buys *model
   round trips and output tokens*, not latency. One call instead of three is
   three fewer chances to mis-call — a 30B argument, and the one the ADR should
   make rather than borrowing P1's numbers.
2. **`compact` profile** (D4) for hook-less clients: compounds, `trace_path`,
   `source_search`, `get_file_outline`, `detect_changes`, `list_projects`, and
   the memory reads. Ten tools, roughly 800 tokens of schemas.
3. **`list_projects` gains `cwd_project`** — the registered project whose path
   contains the server's cwd. It *reports* which scope matches; it does not
   default one, so `2026-10-02-project-routing-is-always-explicit.md` stands.
   `project` stays required everywhere.
4. **`initialize.instructions`**, one short imperative line. Today the
   `initialize` result has no `instructions` at all, so this is the only
   always-on prose channel a hook-less client gets. Verify how each target
   client renders it; pi uses its first line in the `mcp_servers` prompt section,
   only when the extension sets no `description`, character-capped at 250.
5. **`find`'s regex route costs 151ms because it calls the engine's
   `search_code` (116ms), not the in-process zoekt index (28ms).** Preferring
   zoekt for regex-shaped queries is a small local fix worth ~90ms on the
   most-used compound, and it is the only amber row in the budget.
6. **`detect_changes` is 591ms inside the engine, on a clean tree.** Not tk's to
   fix. Keep it out of `compact`, keep it in `scout`/`analysis` with the cost in
   its description, and let the extension run it at `agent_end` where 600ms is
   free.
7. **`list_projects` returns no `path`**, so cwd→project resolution over MCP is
   impossible and the extension would need a CLI spawn at startup. `tk status
   --json` already carries `path`, `state`, `fresh`, `zoekt_fresh` — add those
   fields to the MCP result and the whole startup probe is one engine-free call.
8. **Serialized dispatch is a shared latency floor.** `internal/mcp/server.go:491`
   calls `s.handle` inline, so one slow tool blocks every concurrent call in the
   turn. Items 5 and 6 remove the known offenders; concurrent reads with
   serialized writes is the general fix, it touches a deliberate rule, and it is
   an ADR — P2 at the earliest, not P1.

## Phase 3 — The pi extension

**Executable spec: `2026-10-03-tk-pi-prototype.md`** — layout, the four
gates as code, a six-step build order with a gate per step, and a measurable
definition of done. Read that before starting this phase.

Layout, each file small for the same reason `AGENT_DOCS/` files are:

| file | owns |
|---|---|
| `index.ts` | factory; `registerMcpServer`; config |
| `tk.ts` | `tk` CLI wrapper, `--json` parsing, never a graph call |
| `sections.ts` | `session_start` injection of `tk_project`, `tk_notes`, `tk_ledger` |
| `nudge.ts` | the per-turn relevance probe and its four gates |
| `lifecycle.ts` | `agent_end` sync, ledger delta, shutdown note draft |

Event map: `session_start` (resolve project, ensure resident, sync if dirty,
build sections) — `before_agent_start` (probe; nudge via
`sendMessage(…, {triggerTurn:false})` only when a gate fires) — `tool_call`
(record which tk tools this turn already used, so a turn that asked is never
nudged) — `agent_end` (`tk sync`) — `session_shutdown` (`note_save`, which lands
in the review queue by design).

What it never does: call the graph, declare tk tools itself, or inject per turn
unconditionally.

Every injection is behind an env gate — `TK_PI_SECTIONS` (master),
`TK_PI_PROJECT`, `TK_PI_NOTES`, `TK_PI_LEDGER`, `TK_PI_NUDGE`, `TK_PI_SYNC`,
`TK_PI_RESIDENT`, plus `TK_PI_EXPOSURE` and `TK_PI_PROFILE`. Invalid values are
a hard error at load, never a silent default, matching `resolveProfile`.
`/tk status` prints every effective value with its source.

The `/` surface carries only what env vars cannot: inspect, toggle at runtime,
trigger on demand — `/tk status`, `/tk {sections,ledger,notes,nudge,sync,resident}
on|off`, `/tk expose`, `/tk profile`, `/tk sync`, `/tk recall <query>`,
`/tk note <text>`. `/tk recall` is the one that earns its keep: it runs the nudge
gates and prints which gate passed, so gate tuning is measured rather than
guessed. No `/tk budget` — `jq` over `tk.log` already does it, per the Unix rule.

## Phase 4 — Docs, other clients, and the gate

* Unstub `--client pi` (`internal/cli/setup.go:25`) — the reviewed extension is
  the unblock — and fix `03-COMMANDS.md` in the same commit.
* `mise run docs-man`; bump the `NN-*.md` headers each ADR touches.

  actually renders. That is the only way to learn whether `instructions` and a
  `compact` profile land the way this plan assumes.

  expects 15. `docs-lint` does not check counts, so nothing caught it.

  `2026-10-03-get-graph-schema-unpublished.md`, which is neither on disk nor in
  git history. Its own question is answered by the code above.
* `03-COMMANDS.md:35` documents `--client pi` while `internal/cli/setup.go:25`
  refuses it.

The first and third are fixed by Phases 2 and 4. The second is a gate gap worth
one line in `internal/docs`: every row in `THROWAWAY/INDEX.md` must resolve to a
file on disk.

## Acceptance, one line each

* **P0** — a note holds three measured numbers and the commands that made them.
* **P1** — a fake-engine test asserts zero spawns on the resident path, and
  `04-MCP.md` documents the order.
* **P2** — `tools/list` for `compact` is under ten tools; `find`/`explain` answer
  in one call; `cwd_project` reports without defaulting.
* **P3** — a 30B session over 50 turns runs with no per-turn injection except
  gated nudges, and the sections never re-prefill after the first turn.

## What to do right now

Phase 1, and only Phase 1. Phase 0's gate passed, and its numbers promoted the
resident dial from "the model's latency budget" to the one change that turns a
3-call turn from 5.4s of waiting into under 0.1s. They are the only items with a hard number attached and
everything else is unblocked by them. Phase 2's contract change and Phase 3's
tooling are both downstream of Phase 1's latency result.
